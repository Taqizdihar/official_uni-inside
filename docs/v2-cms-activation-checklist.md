# V2 CMS activation and verification

The owner-supplied `uni-inside-studio-V2.sql` export (2026-10-27) shows an Aiven MySQL 8.4 database with 63 tables. This is a snapshot, not a live connection from this workspace. The repository now enables the storage-supported V2 CMS flags by default in production and declares them `true` in `render.yaml`. An explicitly configured `false` remains a rollback switch. A deployment managed outside the Render Blueprint must update its own environment settings or remove old explicit `false` values.

| CMS area | Dump evidence | Editor behavior after deployment |
| --- | --- | --- |
| Secondary Products, Services, News, Media Kit | Four `page_settings` rows and the typed `secondary_page_content_slots` table with PK, FKs, unique key, and two enforced named CHECKs | Extra text and Product banner slots are editable; missing slots are created on save. The readiness gate checks the actual named constraints. |
| Hero line 3 | `hero_settings.heading_line_3` exists but is `NULL` | Field opens for an approved first edit. Existing two-line public Hero remains until line 3 is saved. |
| About Us editorial | Eleven scalar columns exist but are `NULL`; mission, tag, and collaborator rows are empty | Fields open as an empty draft. A complete valid CMS save initializes scalar fields and three mission points. Public copy stays on its current fallback until that save. No default text is written to Aiven. |
| Homepage News selection | Singleton exists in `latest` mode; no manual placements | Latest/manual controls open. Manual selection still requires published articles. Popular ranking remains unavailable because its source and ordering contract are absent. |
| Contact and Footer | Placement tables, Craft URL, and Maps URL columns exist; placements are empty | Controls open. Choosing a social account requires an active registered account; an empty optional placement list is valid. |
| Social Media and Product media | Twelve platform codes, five mapped active links, and the variant media column/FK exist | Account and variant-media editors open, subject to their existing asset and reference validation. |
| Team template | `team_section_settings.card_template_url` exists but is `NULL` | Authorized administrators can set a template; a template is not invented. |

`SECONDARY_PROJECTS_ENABLED`, `TEAM_MEMBERS_PUBLIC_ENABLED`, and `PARTNERS_PUBLIC_ENABLED` remain off. The dump has no `page_settings` singleton for Projects; managed Team and Partner public replacements also require approved content and behavior. These are separate from enabling supported CMS fields.

For production verification, check the Render backend's effective environment and deployed commit, then load an authorized admin session. `GET /api/v1/admin/secondary-pages/products` should report `capabilities.contentSlots=true` and `contentSlotsReason=null`; repeat for services, news, and media-kit. Check the Hero, About editorial, Homepage News, Contact, Footer, Social Media, Product variant, and Team template editors. Save one approved change, reload its editor, and inspect its public API/page. The About response is initially `enabled=true`, `initialized=false`, `reason=REFERENCE_DATA_PENDING`; that is an editable first-save state, and only a complete validated save changes it to initialized. Public responses may be cached up to 60 seconds.

If a capability remains disabled, `FEATURE_DISABLED` indicates an effective backend flag is still false; `DATABASE_MIGRATION_PENDING` indicates the connected database failed that feature's structural gate. Confirm Render points to the same Aiven database represented by the export. Use [the read-only verification SQL](../backend/migrations/manual-reconciliation/04_verify_v2_cms_activation.sql) for structural details. No production API or Aiven connection was available to this repository run, so live activation and save/reload still require observation after deployment.

The export lists only migration `001` in `schema_migrations`. That ledger discrepancy is separate from V2 editor readiness. Do not replay overlapping DDL or insert ledger rows without reconciling the exact migration scripts and checksums. An explicit `false` on one production flag is the rollback for that feature; it preserves saved V2 data.
