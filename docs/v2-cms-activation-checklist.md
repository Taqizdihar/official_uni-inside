# V2 CMS activation and owner handoff

The owner-reported V2 export is a **snapshot**, not a live Aiven check. It reports 63 tables, four Secondary Page `page_settings` rows (`products`, `services`, `news`, `media_kit`), and just one Secondary content slot (`products.banner_mode = automatic`). It also reports empty About mission/tag/collaborator tables and only `001` in `schema_migrations`. The V2 dump was not attached to this task, and this repository run had no production database or Render access. Run the [read-only DBeaver verification script](../backend/migrations/manual-reconciliation/04_verify_v2_cms_activation.sql) on the intended Aiven database before changing any flags. Export result grids for review; the script changes nothing.

The existing CMS APIs validate requests, preserve legacy fields and public fallbacks, use transactions and audit/revision history, and are protected by session, CSRF, and permissions. All V2 flags default to `false` on Render. “Code-ready” below means a guarded read/save/public path exists and passes isolated tests; it does **not** mean production is active or its current data has been inspected.

## Activation sequence

1. Have the database owner run `backend/migrations/manual-reconciliation/04_verify_v2_cms_activation.sql` in DBeaver against **the same Aiven database Render uses**. Confirm the target database name, Secondary table columns, PK, all three FKs, unique key, typed-value CHECK, the four singleton rows, and absence of malformed slot rows. Compare the Product asset folder to Render's actual `CLOUDINARY_ROOT_FOLDER`. Do not use the export alone as proof.
2. Reconcile migration history separately. A snapshot with V2 tables and only ledger `001` is **not** proof that prepared `002`–`004` are equivalent or registered. Compare exact DDL, constraints, seed data and checksums through the existing `docs/database-audit` process. Never rerun overlapping DDL or insert ledger rows merely to clear a warning. `/api/v1/ready` may report `ready_with_pending_reconciliation`; a checksum mismatch needs investigation before activation.
3. After verified structural results, the authorized Render operator sets **only** `SECONDARY_CONTENT_SLOTS_ENABLED=true` for the backend service and deploys. No frontend flag is required. Leave all other V2 flags at their current values during this first rollout. `GET /api/v1/admin/secondary-pages/{products|services|news|media-kit}` must return `capabilities.contentSlots=true` and `contentSlotsReason=null` for an account with `settings.view`. If false, inspect `contentSlotsReason`: `FEATURE_DISABLED` means backend configuration remains off; `DATABASE_MIGRATION_PENDING` means live storage failed the structural gate. An account additionally needs `settings.update` and a valid CSRF token to save.
4. On one noncritical text field per page, save approved content, reload the CMS and confirm the value, then inspect `GET /api/v1/site` and the corresponding `/products`, `/services`, `/news`, `/media-kit` page. Public API responses can be cached up to 60 seconds. Do not publish test copy to production. For the Product banner, switch automatic → manual with an eligible asset → automatic and reload after each save; verify manual media is projected only when manual mode is selected. A failed save keeps the unsaved CMS draft until the user explicitly discards/reloads it.
5. Activate the remaining flags **one at a time** only after their row in the matrix passes live schema, reference-data, API and public checks. Hero needs approved line 3; About needs the reviewed backfill below; Homepage News manual mode needs published articles; Social/variants need both structural evidence and appropriate data. Keep the four deferred flags/behaviors off as described in the matrix.

For later staged Render activation, the exact backend variable names are `HERO_THREE_LINE_ENABLED`, `ABOUT_EDITORIAL_V2_ENABLED`, `HOMEPAGE_NEWS_SELECTION_ENABLED`, `CONTACT_PLACEMENTS_ENABLED`, `FOOTER_V2_ENABLED`, `SOCIAL_MEDIA_V2_ENABLED`, and `PRODUCT_VARIANT_MEDIA_ENABLED`, each set to the literal string `true` only when its gate is met. Check `GET /api/v1/admin/homepage/hero`, `/admin/homepage/about/editorial`, `/admin/homepage/news/selection`, `/admin/homepage/contact/placements`, `/admin/footer`, and `/admin/social-media/capabilities` respectively, followed by `/api/v1/homepage`, `/api/v1/site`, or the affected product detail. All admin endpoints require an authorized session. Do not set `SECONDARY_PROJECTS_ENABLED`, `TEAM_MEMBERS_PUBLIC_ENABLED`, or `PARTNERS_PUBLIC_ENABLED` as part of V2 activation. Keep `TEAM_TEMPLATE_ENABLED=false` until its separate approval.

## About editorial backfill handoff

The owner must supply and approve real copy for the eleven V2 `about_settings` scalar columns named in `backend/src/services/aboutEditorialV2.ts`, plus exactly three `about_mission_points` for slots 1, 2, and 3 under `about_settings.id=1`. Review optional Studio/Craft workspace tags and collaborator types as well. Check existing production content first; do not replace nonempty values from the website or use preview defaults as a production backfill. The database owner should prepare a separate parameterized, transaction-reviewed data script after approving the text, apply it in a staging copy, verify the resulting rows and public page, then run it on Aiven. This repository intentionally contains no fabricated editorial INSERTs. Only then set `ABOUT_EDITORIAL_V2_ENABLED=true` and verify `enabled=true` on the editorial GET response.

## Recovery and evidence

If a new flag causes an editor/public regression, set that specific Render flag back to `false` and redeploy. Legacy/public fallback paths then take over; the saved V2 rows remain in MySQL for review. Do not delete slots or rewrite the migration ledger as a rollback. For a bad editorial save, use the existing revision/audit trail and an authorized corrective edit. Keep the owner’s DBeaver results, Render deployment ID, before/after API responses (without session headers), and public-page check as activation evidence. Isolated repository tests establish code behavior only; a live end-to-end save and reload is still required to confirm Aiven persistence.
