# Footer CMS implementation and persistence handoff

> V2 update (26 October 2026): Footer social placements and Maps URL now have guarded one-save persistence and public paths behind `FOOTER_V2_ENABLED=false`. The earlier preview-only notes below remain historical; see [the current handoff](aiven-v2-integration.md).

## Current behavior

`/admin/site/footer` is the only Footer menu destination. `/admin/site/site-settings` and its former record URLs redirect to it. The page has one form and one primary **Simpan Perubahan** action. It shows six business inputs: Footer description, Social Media placements, email, phone, location, and Google Maps embed URL. Static Footer navigation links have no editor.

`GET /api/v1/admin/footer` reads the existing `site_settings` record and returns only `footer_description`, `public_email`, `public_phone`, and `address_text`, plus three independent capability indicators. `PATCH /api/v1/admin/footer` accepts and saves only these four columns. It requires a signed-in session, `settings.update`, and CSRF, and uses the existing Site Settings audit/revision flow. The page can use the original `site-settings/1` endpoint if deployed before this backend route; it still sends only the four approved columns. The core form remains editable when Social Media V2 is unavailable.

The public Footer still has brand, fixed navigation, contact, and map regions. Description and physical address render as plain text with line breaks; email and telephone use safe link destinations. The existing four social icons, their destination fallback behavior, and the current Google Maps iframe source remain published. The social area now has a five-column desktop grid so a future authorized selection of up to ten accounts can occupy two rows. No account is automatically published merely because it exists in Manajemen Sosial Media.

## Explicitly pending previews

The Social Media slot picker reads saved accounts through the existing authenticated API, or the V2 account API when that capability is ready. It permits at most ten unique active account IDs, including multiple accounts of the same platform. Left/right controls move account IDs independently of `social_links.sort_order`. The typed future placement shape is `{social_link_id, position}`. The picker and slot grid are **local preview state only**. Their changes are not sent by the Footer save action or rendered on the public website. If an account later becomes inactive or is removed, a future persistent implementation must surface that exact reference for repair, never substitute another account. A persistent relation must enforce unique positions, unique account IDs, a ten-account maximum, and an appropriate deletion policy.

The Maps input accepts only a validated official HTTPS `www.google.com/maps/embed` or Maps Embed API URL and previews it in a fixed-attribute iframe. Raw iframe markup and other hosts are rejected. Its value is **not saved**; the published iframe continues to use the existing URL. The page states both pending limitations beside their controls, retains their unsaved previews after a successful core save, and reports success only for the four persisted fields. Reset clears previews explicitly. The backend capabilities report `footerBaseSettings.enabled=true`, `footerSocialPlacements.enabled=false`, and `footerMapsEmbed.enabled=false` without probing pending schema.

## Related CMS refinements

Social Media account creation and editing no longer ask for an account-global order or active checkbox. New accounts use the backend's safe default active status and order. The card has a permission-aware active switch; its PATCH call is locked while in progress, updates after server confirmation, and leaves the original state intact on failure. The server continues to reject deactivation of an account referenced by a Product. Each card offers **Cek URL** only for a validated platform URL, opens it in a new tab with `noopener noreferrer`, and uses a red danger button for **Hapus** with its existing confirmation dialog.

Product and Service generic edit forms no longer expose global `sort_order`; Article already had no such field. Dedicated Create forms already omitted it. The content listing now defaults to recently updated items, with deterministic ID tie-breaking. Ordered child records, Product variants, service process steps, and Homepage placement order are unchanged. Existing database columns and values are untouched.

## Verification and activation

Frontend typecheck, 39 unit/config tests, and production build passed. Backend typecheck, lint, 106 mocked/unit tests, OpenAPI validation, and build passed. Footer tests cover the four-field write boundary, permissions, CSRF, independent pending capabilities, placement uniqueness and order, and map URL validation. A local browser preview with mocked API responses showed the Footer page at 1280px and 390px without page-level overflow. These checks did not connect the new feature to Aiven or exercise a live database. Browser-level interaction behavior should be checked again during an authorized deployment review.

Permanent Footer placement and Maps editing need a separately approved persistence design and migration. A narrowly scoped proposal is a Footer map-configuration field and a placement association keyed by stable `social_link_id` plus position, with reference integrity and explicit inactive/deletion behavior. The database team should reconcile migration 001 and complete its existing migration plan first. A future backend change must validate all selected account IDs, active status, uniqueness, limit, and map URL before enabling either independent capability. After approval, populate and verify the persistent configuration, then authorize end-to-end CMS and public-Footer checks. This task did not create or execute that migration and did not enable either advanced capability.
