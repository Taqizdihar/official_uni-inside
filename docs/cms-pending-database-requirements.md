Activity History grants its safe, bounded read model to all five established authenticated CMS roles through application policy. Configurable `audit.view` permission records are not rewritten. Raw audit snapshots remain unavailable in that read model.

The initial schema seeds ten callouts whose complete visible lines, including numeric prefixes such as `50+ SHOOTING HOURS`, fit the 30-character limit (the longest is `READY-MADE & CUSTOM PRODUCTS`, 28 characters); production data may differ and should be audited before the new rules are enforced. The unified Hero editor preserves unchanged legacy values that exceed a new visual limit, while validating any edited value. Callout editing maps the complete line back into the existing `numeric_value`, `numeric_suffix`, and `label` columns. It does not offer a third-line preview or claim to save that field while the gate is off.

Hero rollout handoff: deploy the API and editor with `HERO_THREE_LINE_ENABLED=false` first. In the separate database workflow, audit live heading and callout values, rehearse an additive nullable column and reviewed data backfill on an isolated copy, then apply the approved migration and backfill. The legacy first line must become an approved value starting with `Ideas` and having at most nine following characters; line 3 must contain approved nonempty copy, and line 2 must keep its intended meaning. Confirm the existing public two-line response before activation, the new three-line response and animated bulb after activation, and rollback behavior. Turn on the flag only after those checks. Older clients can still read Hero resources but their generic write and revision-restore requests now return 409 and must be moved to the unified endpoint. Later `NOT NULL` enforcement needs a separate review after every live row and client is ready.

No migration or production database operation is included in this Hero task. All proposed scalar columns are additive and nullable initially, with `DEFAULT NULL`. They must not rewrite existing fields or historical migrations. Backfill newly added fields with reviewed live editorial copy, using `backend/src/contracts/aboutTeam.ts` only as a reference for the current source fallback. Do not replace existing Aiven content to match screenshots. Validate character limits and plain text before activation; Clients description remains one value containing intentional blank-line separators.

Proposed collection constraints:

- `about_workspace_tags`: own `BIGINT UNSIGNED` primary key; `workspace_key VARCHAR(32) NOT NULL` references `about_workspaces.workspace_key`; `position TINYINT UNSIGNED NOT NULL` constrained to 1–5; `label VARCHAR(10) NOT NULL`. Unique `(workspace_key, position)` and per-workspace label uniqueness, plus API trimming/NFKC/case-insensitive duplicate checks. Keep workspace identities `studio` and `craft`. Use `ON DELETE RESTRICT` and `ON UPDATE CASCADE`; populate the reviewed Studio and Craft tags independently.
- `about_mission_points`: `slot TINYINT UNSIGNED` primary key constrained to 1–3, `about_settings_id TINYINT UNSIGNED NOT NULL DEFAULT 1` references `about_settings.id`, and `point_text VARCHAR(70) NOT NULL`. Fixed singleton FK with `ON DELETE RESTRICT`. Readiness must verify all three rows; CHECK constraints alone do not guarantee completeness. Backfill the three existing visible points in their current order.
- `about_collaborator_types`: own `BIGINT UNSIGNED` primary key; `about_settings_id TINYINT UNSIGNED NOT NULL DEFAULT 1` references `about_settings.id`; `position TINYINT UNSIGNED NOT NULL` constrained to 1–5; `label VARCHAR(25) NOT NULL`. Unique `(about_settings_id, position)` and normalized labels per singleton. Use `ON DELETE RESTRICT`; backfill the reviewed current labels in display order. An explicitly configured empty list must be distinguishable from a not-yet-activated capability.

Every new table needs an explicit primary key for Aiven's `sql_require_primary_key` policy. These proposals affect both CMS and public copy; Canva affects only CMS. Keep `aboutEditorial`, `workspaceTags`, `collaboratorTypes`, and `teamCardTemplate` capabilities unavailable until schema/constraints, backfill completeness, strict save contracts, and explicit administrator activation are implemented and rehearsed. The current code returns these capabilities as false and never queries their proposed storage. Its supported About save rejects pending properties instead of reporting partial persistence as a full save. The future template mutation must continue to enforce `super_admin`/`administrator` by canonical role code, independently of ordinary content permissions, and must audit changes.

Collection rollout is separate from these schema additions: `TEAM_MEMBERS_PUBLIC_ENABLED=false` and `PARTNERS_PUBLIC_ENABLED=false` are independent default-disabled API configuration flags. Keep them false while cards/logos are being prepared. The original nine Team assets and static Partner assets remain in the repository; none are automatically imported, uploaded, merged, or duplicated. After the owner reviews a complete prepared collection, check desktop/mobile fan/ring and film-roll behavior, approve replacing that collection, and activate only its corresponding flag. A first published record never activates the collection. With an active flag, an intentionally empty published collection shows an empty state. Public cache age remains 60 seconds.

Migration sequence: coordinate with the database owner after current checksum reconciliation and staged 002–004 status is verified; review the scalar additions and child-table constraints above; rehearse an additive migration and reviewed backfill on an isolated copy; deploy schema-ready gated read/write support; verify all fixed rows and permissions; then obtain explicit activation approval. No production environment variable changes are included here. See [Our Team and About Us implementation](our-team-about-us-cms.md) for API contracts, tests, and the manual asset preparation procedure.
