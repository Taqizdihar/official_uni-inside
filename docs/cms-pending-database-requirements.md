# CMS database capability and pending requirements

This is a planning reference, not an authorization to change the schema. The separate database reconciliation work owns migration 001 checksums, missing CHECK constraints, prepared 002–004 migrations, and any Aiven execution. Its live state must be verified independently; repository files alone do not establish which migrations ran in production.

| Capability | Current status | Schema requirement |
| --- | --- | --- |
| Super Administrator manual password reset | Supported by initial schema | Reuses `users.password_hash`, `users.password_changed_at`, `auth_sessions`, `password_reset_tokens`, and `audit_logs`. No new migration. |
| Super Administrator direct member creation | Supported by initial schema | Reuses `users`, `roles`, `user_profiles`, and `audit_logs`. Active account and Argon2id password hash are inserted together; the generated temporary password is returned once and never stored in plaintext. No SMTP or migration required. Existing invited email addresses are rejected rather than activated. |
| Bagian-based Cloudinary image organization | Supported by initial schema | Reuses `media_assets.folder_path` and `public_id` for generic Bagian folders and existing contextual folders. No new migration or rewrite of historical assets. |
| Automatic content URL slugs | Supported by initial schema | Reuses existing unique slug indexes. New records receive collision-safe suffixes; existing URLs remain stable when titles change unless explicitly edited. No new migration. |
| Activity History actor names and friendly labels | Supported by initial schema | Join `audit_logs.actor_user_id` to `users.id`/`users.display_name`; display labels are presentation logic. No new audit name column or migration. |
| Social Media account platform and description | Prepared by separate database work | `social_platforms`, `social_links.platform_id`, and `social_links.description` are in staged 002. Production application status is separately verified by the database owner. |
| Product purchase account reference | Prepared by separate database work | `product_purchase_links.social_link_id` is in staged 003. |
| Product variant image reference | Prepared by separate database work | `product_variants.media_id` is in staged 004. |
| Footer Social Media placements | Proposal only | Persistent ordered references to stable `social_link_id`, unique slot/account rules, limit of ten, and explicit inactive/deletion policy require separately approved design and migration. The current picker is local preview state. |
| Footer Google Maps Embed URL | Proposal only | Persistent URL storage and validation require separately approved design and migration. The current input is local preview state. |
| Contact Us social placements | Proposal only; disabled | Add an ordered mapping from Contact to `social_links.id`, with unique account references, positions, maximum eight, and an explicit inactive/deletion policy. Require Social Media V2 readiness and separately approved migration/activation. The current selector is local preview only. |
| Contact Us Craft URL | Proposal only; disabled | Add a separate nullable HTTPS/path URL field to `contact_section_settings`. It must not reuse `whatsapp_cta_label` or count toward the eight account limit. The current input is local preview only. |
| Homepage News selection | Proposal only; disabled | Add a persisted mode (manual/latest/popular) and a dedicated ordered mapping to existing `news_articles.id`, maximum four with unique references and published eligibility. Do not reuse `is_featured`, article `sort_order`, or subtitle text. The current manual picker is local preview only; public News continues to show the four latest eligible published articles. |
| Homepage News popularity | Pending activation | `news_view` events and daily metrics exist, but a scheduled rollup and completeness of the previous 30 days have not been verified for production. Keep Popular disabled until a verified ranking query, tie-break policy, and saved mode are operational. No new view-count column is proposed. |
| Hero three-line heading | Proposal only; gated off by default | Add nullable `hero_settings.heading_line_3 VARCHAR(18)` to the existing singleton table through a separately approved additive migration. Do not alter migration 001 or the prepared 002–004 scripts. Backfill the new field with reviewed copy and separately reconcile legacy `heading_line_1 = 'Ideas Captured.'` to an approved value starting with `Ideas` and having at most nine following characters, including spaces; preserve the meaning of existing `heading_line_2`. Confirm the public three-line layout, legacy client reads, and rollback with an isolated rehearsal. Only after schema, data, and rendering checks pass should `HERO_THREE_LINE_ENABLED=true` be deployed. The API gate verifies the column and the approved backfill before querying the third line. Leave the new column nullable until every live record has a reviewed nonempty value and clients are compatible; consider `NOT NULL` only in a later approved migration. |
| Missing historical CHECK constraints | Separate reconciliation | Follow the database audit team's reviewed comparison and migration plan. Do not infer their live status from the current repository. |
| Force password change on next login | Optional future security proposal | Would require durable state, such as a reviewed `must_change_password` flag or equivalent, plus login enforcement. It is not part of the approved manual reset. |

Activity History grants its safe, bounded read model to all five established authenticated CMS roles through application policy. Configurable `audit.view` permission records are not rewritten. Raw audit snapshots remain unavailable in that read model.

The initial schema seeds ten callouts whose complete visible lines, including numeric prefixes such as `50+ SHOOTING HOURS`, fit the 30-character limit (the longest is `READY-MADE & CUSTOM PRODUCTS`, 28 characters); production data may differ and should be audited before the new rules are enforced. The unified Hero editor preserves unchanged legacy values that exceed a new visual limit, while validating any edited value. Callout editing maps the complete line back into the existing `numeric_value`, `numeric_suffix`, and `label` columns. It does not offer a third-line preview or claim to save that field while the gate is off.

Hero rollout handoff: deploy the API and editor with `HERO_THREE_LINE_ENABLED=false` first. In the separate database workflow, audit live heading and callout values, rehearse an additive nullable column and reviewed data backfill on an isolated copy, then apply the approved migration and backfill. The legacy first line must become an approved value starting with `Ideas` and having at most nine following characters; line 3 must contain approved nonempty copy, and line 2 must keep its intended meaning. Confirm the existing public two-line response before activation, the new three-line response and animated bulb after activation, and rollback behavior. Turn on the flag only after those checks. Older clients can still read Hero resources but their generic write and revision-restore requests now return 409 and must be moved to the unified endpoint. Later `NOT NULL` enforcement needs a separate review after every live row and client is ready.

No migration or production database operation is included in this Hero task.
